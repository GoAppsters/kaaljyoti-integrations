# Kaal Jyoti for WordPress — design decisions

**Date:** 22 September 2026 · **Status:** settled before code · **Scope:** Tier 3, the wordpress.org plugin (slug `kaal-jyoti`). Wraps the widget bundle for every site and the PHP SDK for sites that render on the server. Listing on wordpress.org is owner-gated (author account, and the licence before any outside site).

## What it is

- A settings page (Settings → Kaal Jyoti), in tabs (decision 19): Connection (publishable key, optional secret key, the connection test; the API address is a `wp-config.php` constant, decision 21), Appearance, Defaults and forms (default city, language, the forms, place search), Reports and PDFs, Advanced (proxy, render mode, cache minutes), Shortcodes.
- Shortcodes `[kj_panchang]`, `[kj_muhurta]`, `[kj_chart]`, `[kj_kundli_form]`, `[kj_match_form]`, `[kj_horoscope]`, `[kj_reading]` with the same attributes as the web components — and since stage 3 of the revamp one per widget, twenty-two (decision 14).
- Seven Gutenberg blocks (twenty-two since stage 3) (`kaal-jyoti/panchang`, `muhurta`, `chart`, `kundli-form`, `match-form`, `horoscope`, `reading`) that render through the same code as the shortcodes.
- Two render modes: **browser** (the default: the page carries the custom elements and the bundled `v1.js` with the publishable key) and **server** (a secret key and the PHP SDK draw panchang, muhurta, chart, preset-horoscope and preset-reading HTML on the server, cached in transients; the two forms, and a horoscope or reading that needs a picker or a birth, are always browser-side).
- A site-wide disclaimer setting for the report elements (horoscope, reading, the kundli form's readings), with per-shortcode/per-block overrides — see decision 11.

```

    readme.txt                      wordpress.org readme

    includes/

      Shortcodes.php                the seven shortcodes → Elements
      Blocks.php                    registers blocks/*/block.json with render callbacks → Elements

    assets/
      widgets/v1.js                 copied from packages/widgets/dist at build (wordpress.org forbids loading scripts from other servers)

  tool/build.mjs                    copies the bundle and the SDK in, writes the autoloader, zips dist/kaal-jyoti.zip

  package.json                      pnpm hooks: build, test, phpcs

```

## Decisions

1. **Bundled, never remote.** wordpress.org guideline 8 forbids loading executable code from other servers, so `v1.js` and the SDK are copied into the plugin at build time rather than loaded from the CDN or installed with Composer. The build writes a tiny PSR-4 autoloader for the SDK's `Kaaljyoti\` namespace so a site without Composer works; if the site's own autoloader already provides `Kaaljyoti\Client`, ours steps aside.

2. **Requires PHP 8.2 and WordPress 6.5.** The SDK's readonly classes need 8.2; 6.5 has `wp_enqueue_script` strategies and the block API the plugin uses. Both are stated in the plugin header and `readme.txt`.

3. **One markup path.** Shortcodes and blocks both hand a sanitised attribute array to `Elements`, which either emits the custom element or calls the server renderer. Attribute names match the web components (`city`, `lat`, `lon`, `timezone`, `date`, `lang`, `show`, `datetime`, `style`, `size`, `varga`, `show-degrees`, `powered-by`); unknown attributes are dropped, every value is escaped with `esc_attr`.

4. **Assets only where used.** The bundle is enqueued from the shortcode/block render path, not on every page; `script_loader_tag` adds `data-key`, `data-base`, `data-lang`, `data-powered-by` and `defer`. The site's origin must be on the publishable key, and the settings page says so with the exact origin (`home_url()` scheme + host + port) to paste into the dashboard.

5. **Server mode is opt-in and secret-key only.** A publishable key is refused without a browser `Origin`, so server rendering needs `kj_live_`/`kj_test_`. The secret key is stored in the options table like every other plugin's API key (WordPress has no secret store) and is masked in the UI. Rendered HTML is cached in a transient keyed by the request hash for `cache_minutes` (default 15); an API failure falls back to the browser widget when a publishable key exists, otherwise renders an admin-only notice and nothing for visitors. Heavy endpoints are never called.

6. **`X-KJ-Client: wordpress/<plugin version>`** on server calls, so usage attributes to the plugin.

7. **Blocks without a build step.** Each block's `index.js` uses `wp.blocks.registerBlockType` and `wp.element.createElement` on the globals; the editor shows the live custom element (the editor iframe calls the API with the publishable key, which costs calls and is said in the block description) with an inspector panel for the attributes. Dynamic blocks: `render_callback` → `Elements`.

8. **Coding standard.** PHPCS with the WordPress standard on the plugin's own PHP (the bundled SDK is excluded; it is PSR-12). Text domain `kaal-jyoti`; every user-facing string is translatable. `uninstall.php` removes options and transients.

9. **Tests.** PHPUnit with Brain Monkey (no WordPress needed): shortcode output for each element, attribute sanitisation and escaping, settings sanitisation (keys by prefix, city id, language enum; the API base constant since decision 21), renderer cache hit/miss and fallback, `WpHttpClient` request/response mapping. Manual QA on a local WordPress (native PHP + the SQLite drop-in, port 3000 so the staging publishable key's origin matches) covering the settings page, both render modes, shortcodes in a post and blocks in the editor. wordpress.org's Plugin Check runs on the same site.

10. **Versioning and deploy.** `0.1.0`, tag `wordpress-v0.1.0`; `.github/workflows/deploy-wordpress.yml` uploads `plugins/wordpress/kaal-jyoti` to wordpress.org SVN with `10up/action-wordpress-plugin-deploy` on the tag, skipped until the `SVN_USERNAME`/`SVN_PASSWORD` secrets exist.

11. **Horoscopes, readings and the disclaimer** (added 28 September 2026, with `POST /v1/horoscope` and `POST /v1/reports/{lagna,nakshatra}`).
    - `[kj_horoscope]` / `kaal-jyoti/horoscope` → `<kj-horoscope sign period date timezone …>`; `[kj_reading]` / `kaal-jyoti/reading` → `<kj-reading type sign|nakshatra | datetime+place …>`; `readings` on the kundli form (`both`/`true`/`lagna nakshatra` → the element's empty attribute, `lagna`, `nakshatra`; anything else off). A bare shortcode word is a flag (`[kj_kundli_form readings]`). Sign and nakshatra ids are whitelisted in `Elements` (the API's snake_case ids; `Purva Phalguni` and `purva-phalguni` are accepted); a reading keeps only the preset its `type` uses, and gets the default city only with a birth time.
    - **House lords** (added with `POST /v1/reports/house-lords`). `type="house_lords"` (`house-lords`, `House Lords` accepted) on `[kj_reading]` and the block's type option ("House lords (needs a birth)"): no preset — a `sign` or `nakshatra` beside it is dropped — and the same birth attributes as a birth-based lagna reading, so it stays in the browser like every birth reading. The kundli form's `readings` also takes `house_lords`: a list of `lagna`, `nakshatra`, `house_lords` (spaces or commas) is written in draw order (`lagna,nakshatra,house_lords`), the two alone still become the empty attribute, `all` is the three, and anything unknown in the list turns readings off. The block offers "Lagna, nakshatra and house lords" and "House lords only".
    - **Personal readings and the summary horoscope** (added with API 0.9.1). `type` also takes `grahas`, `yogas`, `vimshottari`, `varshphal` and `life_areas` (`life-areas`, `Life Areas` accepted); with `house_lords` they are `Elements::PERSONAL_READINGS` — no preset, a birth always, browser-only, and, since the credits contract (decision 20), on every plan at 5 credits each. `year` (four digits, 1800–2400) is kept on a `varshphal` reading (and a `kundli` one) only; without it the element reads the varshphal year running now (this year's from the birth's month and day, last year's before it). `type="kundli"` (API 0.10.1, `POST /v1/reports/kundli`) is in `Elements::TYPES` and `PERSONAL_READINGS` but not in `READING_TYPES`, which is what the birth form's `readings` may name; it takes `parts` (known readings kept in the API's order, comma-separated; none known means no attribute, i.e. all eight) and is priced one call per part. The kundli form's `readings` takes any of the eight in draw order, and `all` is now every reading (eight calls per submit); the block adds "Dashas and the year ahead", "Life areas only" and "Every reading". `[kj_horoscope show_basis="yes"]` / the block's "Transits behind the horoscope" writes `show-basis="true"` (a yes/no like `show-degrees`); without it the reader sees only the summaries — the owner's rule.
    - **Disclaimer.** One setting in the option row — `disclaimer` (`default` | `astrologer` | `off`), `disclaimer_name` (≤ 80 chars), `disclaimer_url` (`esc_url_raw`, http/https, ≤ 200) — so uninstall's single `delete_option()` still covers it. `Elements` resolves it onto every report element it writes: a shortcode's or block's `disclaimer="off"`, `disclaimer="default"` (the API's own line, nothing written) or `disclaimer_name`/`disclaimer_url` wins; otherwise the setting's `disclaimer="off"` or `disclaimer-name`/`disclaimer-url`; the default line writes nothing. The kundli form carries it only when `readings` is on. Block previews resolve the same way from `kaalJyotiBlocks.defaults.disclaimer`.
    - **Server rendering.** A horoscope with a sign and a reading with a preset are drawn by `Renderer` through the SDK (`$kj->horoscope()`, `$kj->reports->lagna()/nakshatra()`), with `options.disclaimer` from the resolved attributes and both languages under `lang="hi"`, as for the panchang. A horoscope without a sign, a reading without a preset, and a reading of a birth (every personal reading is one) return `null` (the browser widget), not a failure. From API 0.9.1 the horoscope card is the answer's summaries: the sign and period, the date line, the `summary` with its level badge (Favourable / Mixed / Needs care — अनुकूल / मिश्रित / सावधानी), then one block per area in the answer's order (work, money, relationships, health, education), each with its label, level and text, and the disclaimer small at the end. With `show-basis="true"` the transits follow in a `<details>`: each graha (the answer's label), the house counted from the sign ("in your 6th house" / "आपके षष्ठ भाव में"), the sign, favourable or not, retrograde except for Rahu and Ketu, and a span only for a transit that enters or leaves inside the period (a day by the clock, a week by day and clock, a month or year by the day; UTC instants converted with `meta.timezone.name`, falling back to its `utc_offset`). There are no scores in the answer and none are drawn.

12. **Google Maps key for the forms' place search** (owner decision, 29 September 2026). An optional `google_maps_key` in the one option row (Place search section, "Google Maps API key (optional)"), sanitised to Google's key alphabet (`[A-Za-z0-9_-]{20,100}`; anything else, and any `kj_…` key, keeps the stored value with a settings error, so a secret key can never be printed this way). It is a browser key like the publishable one — protected by its referrer restriction at Google — so it rides on the bundle's tag as `data-google-maps-key` (re-checked on output), which reaches every `[kj_kundli_form]`/`[kj_match_form]` and block without a per-element attribute. The widgets then search Google Places (new Places API, loaded from Google by the browser; nothing Google is bundled, so guideline 8 is untouched) and send no timezone for a Google pick. `readme.txt` discloses Google Maps Platform as a third-party service (what is sent, when, and links to Google's terms and privacy policy), as the directory guidelines require; nothing goes to Google while the field is empty.
13. **Place search provider and Photon** (owner decision, 30 September 2026). The Place search section adds `place_provider` ("Search with": `auto` — Google Places with a Google Maps key, else Photon; `photon`; `google`; `kaaljyoti` — the API's own `/v1/places` only, no third party), default `auto`, anything else keeping the stored value; and an optional `photon_url` for a self-hosted Photon (https only, normalised to origin + path without a trailing `/` or `/api`; empty, or the public `https://photon.komoot.io`, is stored as empty; anything else keeps the stored value with a settings error). On the bundle's tag a provider other than `auto` is `data-place-provider` and a stored Photon URL is `data-photon-url` (both re-checked on output); the defaults write nothing, since they are the bundle's own. Photon (komoot, over OpenStreetMap data) is called from the visitor's browser, never from the server, so it is a third-party service in the directory's sense: `readme.txt` says what is sent (the letters typed, from the third, plus the fixed query parameters; the browser's IP address and referrer as with any request), when (from the third letter, after a pause, only when a visitor searches "Other place"), and links to Photon, komoot's privacy policy, and OpenStreetMap's copyright and privacy pages. The form shows "© OpenStreetMap contributors" under Photon's results, as OpenStreetMap's licence asks.

14. **Every widget a block and a shortcode** (stage 3 of the revamp, 30 September 2026). The fifteen elements of the revamp join the seven: `Elements::ELEMENTS` is the catalogue (the seven, then the fifteen in the widgets design's order), a shortcode is `kj_` and the element's name with underscores (`[kj_panchang_month]`, `[kj_vimshottari_reading]`), and a block is `kaal-jyoti/<element>`. `Elements` holds each attribute to a rule as before; new are `month` (`YYYY-MM`, 1800–2400), `masa` (`purnimanta`/`amanta`), `system` per element (ephemeris `sidereal`/`tropical`, dasha `vimshottari`/`yogini`), `tab` per element (KP, strength), `tabs` (the kundli form's words, in its order), `time-format` (`12`/`24`, `24h` accepted), `name` (≤ 60 characters), and the switches `chart`, `reading`, `yogini`, `remember` and `pdf`, written only as `off` since on is the element's default. Every element also takes `preset`, `font` (`system`/`inherit`) and `heading` (≤ 80 characters, or `off`) — `Elements::COMMON`, written after the element's own. The calculators get the default city like the kundli form (it pre-fills the place search, or with `datetime` completes a birth); the calculators that end with a reading (moon sign, lagna, life areas, varshphal, dasha reading) take the disclaimer. The new elements are always browser-rendered (`Renderer` returns null for them). **Blocks:** the fifteen describe their panels as data (`blocks/<name>/index.js`, a few lines each) for one shared editor script, `assets/blocks-kit.js` (handle `kaal-jyoti-block-kit`, registered on `init` before the blocks and named in each new `index.asset.php`): a Place or an optional Birth panel, the widget's own choices, and a Display panel — language, theme, preset, font, heading, powered-by, the forms' time format and memory, the disclaimer where there is a reading — plus a notice for the proxy and Growth widgets. Still plain ES5 with no build step (decision 7). The seven older blocks keep their scripts and their attribute names, and gain a Style panel (preset, font, heading) and the forms' new choices (kundli form: tabs; both forms: time format, remember, pdf).

15. **The server proxy** (widgets design decision 23; stage 3). `Proxy` registers `POST /wp-json/kaaljyoti/v1/proxy` (`permission_callback` open: visitors are who calls it, and every check is in the handler). It is on when the `proxy` setting is on and a secret key is stored (`Settings::is_secret_key`), and then — and only then — the bundle's tag carries `data-proxy` with the URL and a `wp_rest` nonce (`_wpnonce`; WordPress's own REST nonce, so a signed-in editor's cookie check agrees with ours), and `data-pdf` with the offered editions when PDF downloads are on. `data-proxy-docs` is always written (the setting, else this plugin's guide), so the no-proxy note sends the owner somewhere useful. The two month widgets render without a publishable key when the proxy is on. **Checks, in order:** proxy on (else `503 proxy_error`); the nonce when `proxy_nonce` is on (else `403 proxy_forbidden` — a setting because a page cache older than a nonce would otherwise break the month widgets; the widgets design's contract says a nonce is optional for that reason); an `Origin` that is not the site's (`403 proxy_forbidden`; WordPress's REST CORS headers would otherwise let another site's page call it); a body over 16 KB (`413`); a content type other than JSON (`415 proxy_bad_request`); `{path, body}` (`400`); the path on the allowlist — `/panchang/month`, `/ephemeris/month`, and with PDFs `/pdf/kundli`, `/pdf/match` — (`403 proxy_path_not_allowed`); and the body rebuilt from the route's fields with their types checked (`400`): a place (numbers in range, an IANA zone or a UTC offset, a label ≤ 120), the month, the ephemeris's `system`, `options.language`; a PDF's birth(s), `edition` (one the site offers, default the first), `name`/`partner_name`, `template` (a preset name), `chart_style` (`north`/`south`), and `options.disclaimer` from the site's setting. A PDF's `branding`, `sections` and `vargas` are dropped: they are the account's. **Cache:** a month's `200 ok` answer is kept in a transient (`kaal_jyoti_px_` + md5 of the API origin, the path and the rebuilt body) for `month_cache_hours` (12; 1–168) and served with `X-KJ-Proxy: hit`, before the rate limit, so it costs nothing. PDFs are not cached here (the API keeps them 24 hours per account). **Rate limit:** a fixed sixty-second window per visitor and bucket (`month`, `pdf`) in a transient keyed by `wp_hash()` of the bucket and `REMOTE_ADDR` (never the address itself; the `kaal_jyoti_proxy_client_ip` filter lets a site behind a CDN say which header to trust), `rate_month` 10 (1–600) and `rate_pdf` 3 (1–60), `429 proxy_rate_limited` with `Retry-After`. An IPv6 address counts by its /64. A PDF path also needs a non-empty `Origin` that is the site's (`403 proxy_forbidden`): a browser's `POST` always sends one, a script need not. **Daily cap:** after the per-visitor limit, each call that reaches the API counts against the site's UTC day per bucket (`kaal_jyoti_cap_<bucket>_<Ymd>`), 500 months and 50 PDFs by default, `kaal_jyoti_proxy_daily_cap` filter (`$cap`, `$bucket`; ≤ 0 is off), `429 proxy_rate_limited` with `Retry-After` to 00:00 UTC. The counters are `wp_cache_add()` + `wp_cache_incr()` (atomic) when `wp_using_ext_object_cache()`, else transients. **The call:** `wp_remote_post( api_base . '/v1' . path )` with `Authorization: Bearer <secret>`, JSON, the widget's `X-KJ-Client` when it is `widgets/<semver>` (else `wordpress/<version>`), no redirects, 20 s (60 s for a PDF). **The answer:** the API's status and JSON body byte for byte (written raw by a `rest_pre_serve_request` filter, since WordPress would otherwise encode the string again), with `X-KJ-Plan`, `X-KJ-Request-Id`, `Retry-After`, `nosniff` and `Cache-Control: private, no-store`; a PDF as the file with `Content-Disposition: attachment; filename="…"` (the API's name when it is `[\w.-]+\.pdf`, else `kundli.pdf`/`match.pdf`); a transport failure or a non-JSON answer `502 proxy_error` with a fixed message — nothing from the failure, which could carry the URL, is relayed. The secret key appears in no answer, header, message or page. `Uninstall` already removes every `kaal_jyoti_` transient, on every site of a multisite network.

16. **Settings of stage 3.** In the one option row: `proxy` (on), `proxy_nonce` (on), `pdf` (off) with `pdf_editions` (`basic` and/or `professional`; PDFs on with none ticked stores `basic` with a note, and PDFs on without a key or the proxy is saved with a warning), `rate_month`, `rate_pdf`, `month_cache_hours`, `time_format` (`12`/`24` → `data-time-format="24"`), `remember` (off → `data-remember="off"`), `font_mode` (`system`/`inherit` → `data-font="inherit"`), `pricing_url` (→ `data-pricing-url`) and `proxy_docs_url`, both http(s) ≤ 200 or empty. Switches are checkboxes with a hidden `0` before them, so an unticked box is posted as off and a field missing from the post keeps what is stored. A new "Server connection" section explains what the secret key enables (the month widgets' cache, PDFs — on every paid plan since decision 20 — and server rendering), that it never reaches a browser, and names the endpoint. "Test connection" (health, then a panchang with the secret key) now also says what the key's plan means: the proxy on or off, the month widgets needing Growth, PDFs needing Scale.

17. **The months open to publishable keys** (owner, 2 October 2026). The API now lets publishable keys call `/v1/panchang/month` and `/v1/ephemeris/month` (still heavy: ten a minute, and since decision 20 a price of 20 credits rather than a plan); the transit scan, the batch match and the PDFs stay closed. So the two month widgets no longer need the secret key: without the proxy they call the API with the publishable key like every other widget, and a key out of credits gets the monthly-limit card. The proxy keeps the month routes on its allowlist as a cache — with a secret key and the proxy on, the page carries `data-proxy`, the widgets prefer it, and a month is answered from a transient for 12 hours instead of from the site's credits on every visit. The month blocks' notices and descriptions no longer ask for a secret key (and, since decision 20, name the price instead of a plan); the settings' Server connection explains the secret key as PDFs plus the month cache (plus server rendering); "Test connection" says the proxy is a cache. The `data-host="wordpress"` flag and the WordPress wording of the no-proxy note, added in the owner's review of stage 3, are removed with the state they worded. Decisions 15 and 16 stand otherwise; where they say the month widgets need the proxy, read "use it when it is on".

18. **Zodiac sign icons** (owner request, 5 October 2026; widgets decision 29). A "Zodiac sign icons" section: `sign_icons` (`element` default, `glyph`, `devanagari`, `custom` — "Your own images"; anything else keeps the stored value) and `sign_images`, one attachment id per sign, chosen with twelve media-library pickers (`wp.media`, images only; a preview and "Clear"; the row is shown only while "Your own images" is chosen). An id is kept only when it is all digits and `wp_attachment_is_image()`; a form that did not post the pickers keeps what is stored; "Your own images" with none chosen is saved with a warning. **Output:** the ids are resolved at render time to the `medium` size's URL (big enough for the picker on a high-density screen, never the original upload; WordPress gives the full image when an upload is smaller), and a URL is written only when it is `https://`, or this site's own — then as a path (`/wp-content/uploads/…`), so a local site over plain HTTP still gets its images; anything with a quote, bracket, backslash or space is refused. With images, `data-sign-icons` is their JSON map (`wp_json_encode` with the `JSON_HEX_*` flags, then `esc_attr`) and, when the site's theme is another, `"theme"` in the same map, so a block set to "the site's own images" has them while the rest of the page keeps the site's theme; without images it is the theme's name, or nothing for `element` (the bundle's default) and for "your own images" with none usable. An attachment deleted since it was chosen drops out. **Per block:** `sign-icons` (`Elements::SIGN_ELEMENTS`, the thirteen elements that show a sign; written after `COMMON`) with a "Sign icons" select in the Display panel (site default and the four), and `sign_icons="…"` on the matching shortcodes. The server renderer draws no sign icons (its markup has none).

19. **The settings page in tabs** (owner request, 5 October 2026: "so many settings … difficult to locate"). WordPress's own `nav-tab-wrapper` / `nav-tab` links on the one page, `options-general.php?page=kaal-jyoti&tab=<slug>`, as WooCommerce does: no JS framework, and it works without JS. The tabs, in order (the first is the default, and any unknown `tab` is the first): **Connection** — publishable key with the origin to add to it, secret key (the "Advanced: API address" section with the base URL was removed by decision 21); the "Test connection" button below the form. **Appearance** — style preset, theme, the seven colours, type (`font_mode`), font, corner radius, "Powered by", and the zodiac sign icons with the twelve pickers. **Defaults and forms** — default city and language (they apply to every widget, hence not just "Forms"), birth time format, remember birth details, place search provider, Google Maps key, Photon URL. **Reports and PDFs** — the disclaimer with the astrologer's name and link, PDF downloads and editions. **Advanced** — the server connection (proxy, nonce check, the two per-visitor limits, month cache hours), server rendering (render mode, cache minutes), and the pricing and setup-guide links of the owner notes (they serve the plan and monthly-limit notes of every widget, so they stay here rather than under Reports). **Shortcodes** — read-only: every example shortcode with a Copy button (drawn `hidden`, shown by `admin.js` when the clipboard API exists). Each tab opens with a one-line description of what it holds.
    - **Registration.** Sections and fields are tables (`Settings::sections()`, `Settings::fields()`); each section is registered on a per-tab page id (`kaal-jyoti-<tab>`) so `do_settings_sections()` draws one tab. `Settings::tab_keys()` is the keys a tab owns: its fields plus the inputs drawn inside them (`disclaimer_name`, `disclaimer_url`, `pdf_editions`, `secret_key_remove`). A test holds every stored key to exactly one tab.
    - **Saving one tab never resets another.** Each tab is its own form posting to `options.php` (same group, same `kaal_jyoti-options` nonce, same `manage_options` capability) with a hidden `kaal_jyoti_settings[_tab]`. `sanitize()` lays the tab's posted keys over the stored row and runs the usual rules on that merged row (so cross-field rules — PDFs needing the proxy and the key, server rendering needing the key — see the real values); then every key the tab does not own is written back exactly as stored, whatever was posted. Missing fields: an on/off setting (and the PDF editions) absent from the post is off only when it belongs to the saved tab; any other missing key keeps its stored value. A post with no `_tab` at all — `update_option()` from code — is the old whole-row save.
    - **Errors on their tab.** While a tab is sanitised, `add_settings_error()` runs only for errors about that tab's keys (`Settings::error()` names the keys an error is about; "PDFs on without the proxy" is about `pdf` and `proxy`, so it shows on Reports and on Advanced). `options.php` redirects to the referer, which carries `&tab=`, so "Settings saved" and the errors appear on the tab that was saved. The page no longer calls `settings_errors()` itself: `wp-admin/options-head.php` already prints them on a Settings page, and the second call showed every error twice.
    - **Assets per tab.** The colour pickers and `wp_enqueue_media()` load on Appearance only; `admin.js` (connection test, search, copy) everywhere on the page, each part a no-op when its markup is absent.
    - **Search settings.** A plain-JS box (drawn `hidden`, so absent without JS) hides the current tab's rows that do not match (and a section left with none), and lists matching field labels on the other tabs as links to them, from `Settings::search_index()` passed through `wp_localize_script()`.
    - **Links.** `Settings::tab_url( $tab )` builds the tab's URL; the admin-only "add a publishable key" notice links to Connection, and the block help texts, the month blocks' descriptions and `readme.txt` name the tab ("Settings → Kaal Jyoti → Appearance").

20. **Credits, not calls** (5 October 2026). The API bills in weighted credits and no plan gates a route any more: a calculation costs 1 credit, a written reading or a horoscope 5 (a kundli report 5 per part), a month of panchang or ephemeris 20, a kundli PDF 1,000 and a match PDF 500. The one thing a plan still decides is PDFs — every paid plan has them, with a monthly cap (Starter 50, Growth 200, Scale 500, Enterprise 2,500), and Free has none. So: every notice, block description, help text and readme line that named the Growth or Scale plan now names the price; the `growthNote` editor string is `readingNote`; "Test connection" no longer says the month widgets need a plan, and for PDFs says only whether the plan is Free (`plan_required`) or paid. A site out of credits gets `402 quota_exceeded`, which the widgets draw as the "Monthly limit reached" card. The proxy relays `X-KJ-Plan`, `X-KJ-Request-Id` and `Retry-After` only (its allowlist, unchanged): `X-KJ-Credits-Remaining`, which the API sends to the site's secret key, is the account's balance and never reaches a page — a test holds it. The server renderer reads nothing of the old contract (`meta.calls`, `X-KJ-Calls`); the bundled PHP SDK now exposes `Result::$credits` and `$creditsRemaining`, which the plugin does not show. The powered-by rule (decision on the footer: hidden only on growth, scale and enterprise) is not an API gate and is unchanged.
21. **The API address is a constant, not a setting** (owner decision, 6 October 2026). Site owners never need to change it, and a visible field invites breakage and reviewer questions, so the Connection tab's "Advanced: API address" section and its `base_url` field are gone. `Settings::api_base()` is the one reader — the server proxy, server rendering (the SDK's `baseUrl`), the bundle's `data-base` and "Test connection" all call it — and answers the `KAAL_JYOTI_API_BASE` constant from `wp-config.php` when it is defined and passes `normalize_base_url()` (https, origin only, a trailing `/` or `/v1` trimmed), else `PRODUCTION_BASE_URL`. An invalid constant is ignored. While the constant is defined, the Connection tab shows a one-line note with the address in use (a warning instead when it was ignored); without it, nothing. `base_url` left the defaults, so a value stored by an earlier build (the QA site had staging) is never read and drops out of the row at the next save. The version first submitted to the directory keeps the field; this applies from the first SVN upload after approval.

## Out of scope for 0.1.0

Widget styling options in the customiser, per-post birth data storage, WP-CLI commands, multisite network settings.
