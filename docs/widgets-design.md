# `@kaaljyoti/widgets` — design decisions

**Date:** 22 September 2026 · **Status:** settled before the first line of code · **Scope:** Tier 1 of the distribution plan (the web-component bundle). Later packages get their own page here.

## What it is

One script tag, twenty-two custom elements (seven at 0.1.0, fifteen more in stage 2 of the revamp — the catalogue below), no framework. Since the revamp (decision 20) the script is a small loader that fetches each element's code the first time the page has one:

```html
<script src="https://cdn.kaaljyoti.com/widgets/v1.js" data-key="kj_pub_…" defer></script>

<kj-panchang city="delhi" lang="hi"></kj-panchang>
<kj-muhurta city="mumbai"></kj-muhurta>
<kj-chart
  datetime="1990-05-14T10:30:00"
  timezone="Asia/Kolkata"
  lat="28.6139"
  lon="77.209"
  style="north"
  size="360"
></kj-chart>
<kj-kundli-form tabs="overview charts planets dasha life"></kj-kundli-form>
<kj-match-form></kj-match-form>
<kj-horoscope sign="aries" period="daily"></kj-horoscope>
<kj-reading type="lagna" sign="leo"></kj-reading>
<kj-panchang-month city="delhi"></kj-panchang-month>
<kj-moon-sign></kj-moon-sign>
<kj-dasha></kj-dasha>
```

Everything talks to `POST /v1/...?key=kj_pub_…` exactly as the embed recipes in the API docs do. The bundle adds no calculation; it adds auth, request shapes, caching, error mapping, i18n and markup.

## Design system (revamp, 30 September 2026)

The owner's verdict on 0.1.0 was that the widgets worked and did not look like a product. Stage 1 of the integrations revamp (`internal-docs/integrations-revamp-plan.md` §1–§3, §5) gives every widget one visual system, drawn from the PDF templates (`kaaljyoti-engine/crates/kj-pdf/templates`) so a site's PDFs and widgets read as one product. Written before the code; the decisions below it say how each piece was built.

### Tokens

Every token is a `--kj-*` custom property declared on `:host`, so a page rule on the element beats it in every mode (decision 1 still holds; nothing needs `!important`).

| Group          | Tokens                                                                                                          | Notes                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Ground and ink | `--kj-bg`, `--kj-text`, `--kj-muted`, `--kj-line`                                                               | `--kj-line` stays the chart's line colour                                          |
| Surfaces       | `--kj-surface` (card), `--kj-tint` (header band, selected tab, tiles), `--kj-border` (hairlines), `--kj-shadow` | `--kj-surface` is still undeclared by default, so `--kj-bg` alone recolours a card |
| Accent         | `--kj-accent` (= `--kj-lagna`), `--kj-accent-2` (gold/saffron ornaments), `--kj-on-accent`                      |                                                                                    |
| Meaning        | `--kj-good`, `--kj-bad`, `--kj-care`, `--kj-planet-<graha>`, `--kj-retro`                                       | the chart SVG's names, unchanged                                                   |
| Type           | `--kj-font` (body), `--kj-font-heading`, `--kj-size` (base, 15px)                                               | Devanagari stack below                                                             |
| Shape          | `--kj-radius` (12px), `--kj-space` (1em rhythm)                                                                 |                                                                                    |

**Type scale** (em of `--kj-size`, which is px so a theme's `html { font-size: 62.5% }` cannot shrink it): title 1.25 (≈19px), section head 1.0625, body 1, secondary 0.875, caption 0.8125 — nothing smaller, and only captions and badges at that size. Body line-height 1.55; `:lang(hi)` text 1.75, because Devanagari's matras need the room. **Fonts**: no web font is loaded (a font request is a third-party call and a shadow root cannot declare `@font-face` anyway). Latin text uses the system UI stack; Hindi puts `'Noto Sans Devanagari', 'Mukta', 'Kohinoor Devanagari', 'Nirmala UI', 'Mangal'` first; the serif presets head in `'Noto Serif', Georgia, serif` with `'Noto Serif Devanagari'` behind it. A page that loads Mukta or Noto gets them.

**Contrast**: body text on each preset's ground is at least 7:1, muted text at least 4.5:1, the accent on its tint at least 4.5:1; good/bad hues are paired with a word or an icon, never colour alone.

### Presets

`preset` on an element, `data-preset` on the script, `configure({ preset })`; unknown values fall back to `classic`. A preset sets the accent family, the heading face and the header style; the theme (`auto` / `light` / `dark`, decision 1) still sets ground and ink, so 4 presets × 3 themes all work, and `--kj-*` still overrides both.

| Preset              | From the PDF    | Accent / second                                      | Ground (light)  | Heading | Header                                        |
| ------------------- | --------------- | ---------------------------------------------------- | --------------- | ------- | --------------------------------------------- |
| `classic` (default) | classic.typ     | maroon `#7A1F2B` / gold `#B08D57`                    | cream `#FCFAF4` | serif   | title, thin accent rule                       |
| `modern`            | modern.typ      | teal `#1B5E7A` / amber `#E0A63A`                     | white           | sans    | solid accent band, light text                 |
| `minimal`           | minimal.typ     | ink `#222` / grey                                    | white           | sans    | plain title, hairline                         |
| `traditional`       | traditional.typ | maroon `#7A1424` / saffron `#D9780F`, gold `#C49A2C` | `#FFFBF2`       | serif   | tinted band, gold rule with a saffron diamond |

Dark variants lift each accent to a light tint of itself (maroon → amber `#E8B04A` as in 0.1.0, teal → `#6CC0E0`).

### Components

All are HTML-string helpers in `core/ui.ts` plus rules in `styles/base.css`; none is a custom element of its own.

- **Card** (`KjElement.paint`): `article.kj-card[part=card]` → `header.kj-head[part=header]` (title, subtitle for place/date, accent rule; `heading="…"` replaces the title, `heading="off"` drops the header) → `div.kj-body[part=body]` → `footer.kj-foot[part=footer]` (disclaimer, powered-by).
- **Tiles**: a responsive grid (`minmax(9.5em, 1fr)`) of label / value / sub-line blocks — the panchang limbs, the kundli overview.
- **Day timeline**: a bar from sunrise through sunset to the next sunrise, segments positioned by wall-clock minutes (decision 7: components, never a `Date` in the reader's zone), coloured good/bad, sunrise/sunset/now ticks, a legend, and the same windows as a list under it for screen readers and for exact times.
- **Data table**: tabular figures, a sticky first column, horizontal scroll inside the card on a phone; sign names carry their icon (decision 29; until 0.2.0 a Unicode glyph, `♈︎`… with U+FE0E).
- **Badges**: small pills — retro ℞, vargottama, dignity (exalted, own sign, debilitated…), current, level (favourable / mixed / needs care).
- **Tabs**: `role=tablist` / `tab` / `tabpanel`, `aria-selected`, roving `tabindex`, ←/→/Home/End; panels render lazily.
- **Segmented control**: a row of `aria-pressed` buttons for small exclusive choices (chart style, day, period).
- **Buttons**: primary (accent fill) and quiet (outline).
- **Skeleton**: shimmer blocks shaped like the widget; static under `prefers-reduced-motion`; carries a visually hidden "Loading…" in a `role=status`.
- **States**: empty, error (translated line, decision 6) and **plan required** (below), each a small centred block with an icon.
- **Ring gauge**: an SVG circle for the match total.

### Plan-required state

Every site gets every widget, and since the credits contract (5 October 2026) every plan can call every route a widget uses: the month's credits do the limiting, and the one thing a plan still decides is PDFs, which are not on Free. A `402 quota_exceeded` (the month's credits are used up) or a `403 plan_required` (a PDF on the Free plan) is never shown raw: a polite card says the monthly limit is reached, or that the section needs a paid plan, and a small line for the site owner links to the pricing page (`pricing-url` / `data-pricing-url` / `configure({ pricingUrl })`, default `https://kaaljyoti.com/api/pricing`). Inside a tabbed report the state fills that tab only.

## Decisions

1. **Shadow DOM, themed through custom properties.** Every element renders into an open shadow root so a host theme's `dl`/`table` resets cannot break it. Colours and type come from `--kj-*` custom properties, which cross the shadow boundary. The shadow stylesheet declares defaults on `:host` for the same sixteen `--kj-*` names the chart SVG uses (`--kj-bg`, `--kj-text`, `--kj-line`, `--kj-lagna`, `--kj-muted`, `--kj-planet`, `--kj-planet-<graha>`, `--kj-retro`) plus a handful of widget-only ones (`--kj-font`, `--kj-radius`, `--kj-surface`, `--kj-accent`, `--kj-good`, `--kj-bad`). The API's SVG scopes its own defaults to `:root`, which does not match inside a shadow tree; declaring them on `:host` is what makes an inlined chart pick up the page's theme. Blocks carry `part="…"` names for `::part()` overrides. Three modes via a `theme` attribute (default from `data-theme` / `configure({ theme })`): `auto`, the default, has no card background and derives its neutrals from `currentColor` and its hues from `light-dark()` (with a `prefers-color-scheme` fallback), so a widget blends into a light or a dark site; `light` is the original cream card; `dark` is its dark counterpart. Each mode's values are still `:host` declarations, so a page's `--kj-*` beats them in every mode.

2. **The key comes from the script tag or from `configure()`.** `v1.js` reads `data-key`, `data-base` (defaults to the production origin), `data-lang` (`en`), `data-theme` (`auto`), `data-powered-by`, and for the forms' place search `data-google-maps-key`, `data-place-provider` and `data-photon-url` (decision 16), from `document.currentScript` — and since the revamp `data-preset`, `data-remember`, `data-time-format`, `data-pricing-url` and `data-chunks` (decisions 17–22), with the same names in `configure()`. The ESM build exports `configure({ key, baseUrl, lang, theme, googleMapsKey, placeProvider, photonUrl })` and `define()` and registers nothing until `define()` is called, so bundlers and frameworks stay in control. A missing key renders a visible, translated "no key" state rather than throwing.

3. **Staging is a base URL, not a build.** One bundle; `data-base="https://api-staging.kaaljyoti.com"` (origin only, `/v1` is added) points it at staging. This session builds and QAs against staging with the seeded publishable key whose allowed origins include `http://localhost:3000`, so the examples server listens on 3000.

4. **One call per distinct request per page load.** The client memoises by `path + canonical JSON body` and dedupes in-flight requests, so three widgets asking for the same day at the same place make one `/v1/panchang` call. The muhurta strip renders from the daily panchang document (Brahma muhurta, Abhijit, Rahu kaal, Yamaganda, Gulika are all in it), so `<kj-panchang>` plus `<kj-muhurta>` for the same city is still one call. `POST /v1/panchang/muhurta` adds the choghadiya and hora tables; it takes either a birth (and then adds Tara/Chandra bala against the natal Moon) or just a place and date like `/v1/panchang`, and a strip built on it is deferred to a later minor. _Revamp:_ `<kj-muhurta>` now draws the choghadiya from `/v1/panchang/muhurta` (decision 21), so beside a panchang it is a second call.

5. **`X-KJ-Client: widgets/<version>`** on every request; the version is injected at build time from `package.json`.

6. **Errors are rendered, never thrown to the page.** The envelope's `error.code` maps to a translated one-line state inside the widget (`forbidden_origin` says which origin to add; `rate_limited` retries once after `Retry-After`, capped at 10 s, then shows the message; `quota_exceeded` and `plan_required` are shown as-is). A `kj-error` DOM event bubbles for site owners who want to know.

7. **Wall clocks are strings.** Every `…T06:13:13.728` in a response is a wall clock at the place. The formatter slices, it never constructs a `Date` from one. Dates for `date="…"` attributes are validated as `YYYY-MM-DD`; `date="today"` (the default) sends no `date`, which the API treats as today at the place.

8. **Places.** `city="delhi"` resolves against the bundled list (the landing page's eight cities today, the 500-city list later, same shape). `lat`/`lon` (+ optional `timezone`) override the city; with neither, the element shows the "no place" state. The kundli form offers the city list plus, behind "Other place", a place search and a manual coordinates row; it sends no `timezone` for manual entry, letting the API derive it. See decision 16 for the search. _Revamp:_ the forms have no city list any more; the search is the place field and `city` only pre-fills it (decision 18).

9. **Powered by.** A "Powered by Kaal Jyoti" link is rendered by default. `powered-by="hidden"` (attribute or `data-powered-by` on the script) is honoured only when the response's `X-KJ-Plan` header is `growth`, `scale` or `enterprise`; on `free` and `starter` the link stays. No API change needed; the plan-feature flag from the plan document can replace this check later.

10. **Language.** `lang="en" | "hi"` per element, falling back to the script's `data-lang`. Requests always ask for `["en","hi"]` so a language switch re-renders without a second call. Widget chrome (labels, error strings) comes from a bundled dictionary; entity names come from the response's `names.<lang>`.

11. **Calls per element.** `<kj-panchang>` 1, `<kj-muhurta>` 0 extra when a panchang for the same place/day is on the page (else 1), `<kj-chart>` 1, `<kj-kundli-form>` 1 per section in `show` (`summary` → `/v1/kundli`, `chart` → `/v1/kundli/chart`) per submit, `<kj-match-form>` 1 per submit (`/v1/match/ashtakoot`, both births in one body; open to publishable keys — only `/v1/match/batch` is heavy), `<kj-horoscope>` 1 per sign, period and day (none until a sign is chosen), `<kj-reading>` 1 (none until it has a sign, a nakshatra or a birth; a personal report only ever a birth), and `readings` on the kundli form 1 more per reading per submit (`lagna`, `nakshatra`, and the personal reports only when named) — off by default, so a page that does not ask pays nothing new. An identical resubmit on either form is answered by the page memo. Documented in the README so a site owner can forecast a bill: since the credits contract a call is 1 credit for a calculation, 5 for a reading or a horoscope and 20 for a month (`https://kaaljyoti.com/api/docs/credits`). _Revamp:_ the kundli form's report and the match form ask for more; decision 19 has the new numbers.

12. **Versioning and outputs.** Package `0.1.0`, tag `widgets-v0.1.0`. `dist/v1.js` is the CDN file (major only, minors roll forward) plus a pinned copy `dist/v<semver>.js` (`v0.1.0.js`); `dist/index.js` + `dist/index.d.ts` for npm. Size budget 24 KB gzipped for `v1.js` (20 KB until the personal readings arrived, 22 KB until the place search did — decision 16), enforced in CI. CDN upload and npm publish are owner-gated release steps. The CDN is the R2 bucket `kaaljyoti-cdn` on `https://cdn.kaaljyoti.com/widgets/` (set up 2026-10-05; CORS: any origin may GET). `pnpm cdn:publish` (`scripts/publish-cdn.mjs`, `--dry-run` to preview) uploads every chunk not yet there (a year, `immutable`), the pinned `v<semver>.js` (immutable; the run stops if that version is already published with other bytes — bump the widgets version before every publish), and `v1.js` last (5 minutes). Nothing is ever deleted, so a cached or pinned loader always finds its chunks. The zone's Browser Cache TTL is set to respect existing headers, so those cache lifetimes reach browsers as written.

13. **Tests.** Unit tests against recorded fixtures with a mocked `fetch` (shape, caching, error mapping, rendering, language switch); a live smoke test against staging that runs only when `KJ_PUB_KEY` is set (sends `Origin: http://localhost:3000` from Node). CI runs the unit tests only.

14. **Reports: readings and a horoscope, with no scores.** `<kj-horoscope>` (`POST /v1/horoscope`) and `<kj-reading type="lagna|nakshatra|house_lords">` (`POST /v1/reports/lagna`, `/v1/reports/nakshatra`, `/v1/reports/house-lords`) render text an astrologer wrote, keyed by language (`{ en, hi }`, both asked for per decision 10). Nothing is scored: no percentages, meters or lucky numbers, because the API has none and a widget that made them up would be claiming a precision the readings do not have. The pickers need names before any answer exists, so the twelve signs, twenty-seven nakshatras and nine grahas are bundled in the engine's spelling (`core/reports.ts`); an answer's own label wins where there is one. A pick writes the element's attribute (`sign`, `period`, `date`, `nakshatra`), so the one-load-per-change rule does the rest. A horoscope's `from`/`to`/`entered`/`leaves` are UTC instants rather than wall clocks: they are converted with `Intl` in the zone `meta.timezone` names (the fixed `utc_offset` as a fallback), never the reader's, and then sliced like any other wall clock. Every report answer ends with the API's disclaimer line unless `disclaimer="off"`; `disclaimer-name`/`disclaimer-url` make it name the site's astrologer. One reading element serves all three types, which keeps the WordPress wrapper to one more element instead of three. The house lords take a birth only (no picker; the chart's `no_birth` line without one) and draw twelve items in house order — a heading of the house, its sign, its lord and the house the lord sits in ("1st house · Gemini · lord Mercury in the 9th" / "प्रथम भाव · मिथुन · भावेश बुध नवम भाव में", the ordinals shared with the horoscope in `core/reports.ts` and the names the API's `names`), then the reading — and the disclaimer once, at the end.
15. **Summaries, not planet lists.** From API 0.9.1 (engine 0.9.1) `POST /v1/horoscope` answers `{sign, period, from, to, summary: {level, text}, areas: [{area, level, text}], basis: [...]}` — one summary and five areas (work, money, relationships, health, education), each `favourable`, `mixed` or `care` — instead of a per-graha map. The owner's rule: the reader sees the summaries, never the per-planet list. So `<kj-horoscope>` draws the summary first, then five area cards, each with a level badge (Favourable / Mixed / Needs care — अनुकूल / मिश्रित / सावधानी; a word in a pill, never a number), and `basis` only when the page sets `show-basis` (folded away, with the entered/leaves times the old per-graha view showed). The same rule shapes the new personal readings on `<kj-reading>`: `grahas` (nine items, sign and house and both texts), `yogas` (the API's `name`, keyed by language from API 0.10.1 — the bundled table of 38 names it replaced is gone — participants, text), `vimshottari` (each mahadasha a heading with its dates, level and text, the current one marked; the antardashas are not drawn), `varshphal` (`year`, default the varshphal year running now — this year's from the birth's month and day, last year's before it, never before the birth year; summary, seven areas and the mudda periods as dated chips) and `life_areas` (summary line and eleven area cards). None draws `basis`. They were Growth-plan reports until the credits contract (5 October 2026); now every plan can call them, at 5 credits each, and the refusal one can meet is the monthly limit (decision 22). Instants in these answers (dasha and year dates) are read in `meta.timezone`, as the horoscope's are. The kundli form's `readings` accepts all eight types; the personal ones only when named. The level and area labels are chrome (`core/i18n.ts`), in the engine's own wording for the life areas. `type="kundli"` (API 0.10.1, `POST /v1/reports/kundli`) asks for several parts at once — `parts`, default all eight, priced one call per part — and draws each with the same renderer as its own type, in the answer's `parts` order, each in a `section-<part>` with the part's name as a heading (the lagna, nakshatra and varshphal carry their own), and one disclaimer at the end; it sends `year` only when written, since the API works out the running year itself. Adding the personal readings took `v1.js` from 18.1 KB to 20.6 KB gzipped, so the budget in decision 12 moved from 20 to 22 KB; with the yoga table gone and the kundli report added it is 20.2 KB.

16. **Place search: Google with the site's key, else Photon, else `/v1/places`** (owner decisions, 2026-09-29 and 2026-09-30). "Other place" on both forms opens a search box above the latitude/longitude row. Our index covers places of 1,000+ people; Google and OpenStreetMap find villages. **Provider**: `place-provider` on the form (or `data-place-provider` / `configure({ placeProvider })`), one of `auto` (default), `google`, `photon`, `kaaljyoti`. `auto` is Google Places when the form has a Google Maps key (`google-maps-key`, `data-google-maps-key`, `configure({ googleMapsKey })`), else Photon; `google` and `photon` pin one; `kaaljyoti` asks only `GET /v1/places` (metered, one call per search, publishable keys allowed, memoised per query, picks carry their zone) — for sites that want no third-party call. Every provider falls back to `/v1/places`. **Photon** (komoot's OpenStreetMap geocoder; Nominatim's usage policy forbids autocomplete on its public server, so it is not an option): `GET {photon-url}/api/?q=…&limit=8&lang=en&osm_tag=place`, `photon-url` defaulting to `https://photon.komoot.io` so a site (or we, later) can point at a self-hosted Photon. `lang=en` for both page languages: the public server has names in only a few languages and falls back to the local name; the name returned is shown as it is. `osm_tag=place` keeps populated places; features whose `osm_value` is country, state, region, province, continent, archipelago, ocean or sea are dropped. **No location bias** (`lat`/`lon` unset): a bias would bury a birth abroad under Indian namesakes. A line reads "name, district, state, country" (Photon's `county`, since two villages of one name in one state are common; duplicates collapse); a pick sends the label "name, state, country", the coordinates and **no timezone**. Good-citizen rules for the free public server: 300 ms debounce, 3 characters, one request in flight (aborted by new letters), the same letters asked once per page, no prefetch and no retry; an HTTP error, a non-JSON answer or no answer in 4 s drops Photon for the page with one `console.warn` and the search goes on with `/v1/places`. The request carries no Kaal Jyoti key and no custom headers. The list shows "© OpenStreetMap contributors" (hi: "© OpenStreetMap योगदानकर्ता"), linked to https://www.openstreetmap.org/copyright, under Photon's places (not under an empty list). **Google**: a Google Maps key switches `auto` (and `google`) to Google Places. Rules: the Maps JS API is loaded from `maps.googleapis.com` (`loading=async&libraries=places&callback=…`, `language` = the form's) once per page, lazily on the first search, never bundled; a page that already loaded Maps is reused. Only the **new** Places API is used — `AutocompleteSuggestion.fetchAutocompleteSuggestions` with an `AutocompleteSessionToken` per session (first keystroke → pick), then `Place.fetchFields(['location','displayName','formattedAddress'])`, which ends the session — because the legacy `places.Autocomplete` is closed to new Google customers, and our own dropdown keeps the widget's look. `language` is the widget's (`en`/`hi`), `region` is `in` (a bias, not a restriction). The dropdown shows Google's required attribution as the text "Google Maps" (Roboto 400, 12px, #5e5e5e / white — Google's current attribution guidelines accept that text where the logo does not fit, and forbid translating it) whenever Google results are shown. A Google pick sets lat/lon and `place` (formattedAddress, cut to the API's 120 characters) and **no timezone**: the API derives the historical zone from the coordinates (`meta.timezone.source = "derived"`). A `/v1/places` pick sends the zone it came with. Typing coordinates drops a picked zone and label; typing in the search box drops the last pick. Fallback: the script failing to load (or 10 s passing), `gm_authFailure`, or a rejected suggestion request drop Google for the page with one `console.warn` — to Photon under `auto`, to `/v1/places` under `google`; the form never breaks and the coordinates always work. Searches start at 3 characters after a 300 ms pause. Keyboard: arrows, Enter picks (not a submit), Escape closes. The build collapses the indentation of `html` templates (whitespace runs with a newline become one space, which renders identically), which saves about 0.3 KB; even so, Google took `v1.js` to 22.6 KB and Photon to 23.0 KB gzipped, so the budget in decision 12 moved from 22 to 24 KB (owner to confirm). _Revamp:_ the one-file budget is gone with the one file; decision 20 has the loader's and the chunks'. The search itself is unchanged, and is now the forms' only place field (decision 18).

17. **The design system** (revamp; the section above). Every widget is a card drawn by the base class: `article.kj-card[part=card]` with a header band (`heading()` in the subclass; `heading="…"` replaces the title, `heading="off"` drops it), a body, and a footer holding the report's disclaimer (`footerNote()`) and the powered-by link. `frame="none"` draws an element without its card, which is how the kundli form nests a chart or a reading inside its own. Presets (`preset`, `data-preset`, `configure({ preset })`) set private `--kj-p-*` values that the three themes turn into the public tokens, so every existing `--kj-*` override still wins. `preset` is reflected from the config onto the element like `theme`. Components are string helpers in `core/ui.ts` (no nested custom elements); `html.ts` is split out of `element.ts` so both can use it. Class names the API's chart SVG uses are never put on HTML: its `<style>` lands in the shadow root. Container queries (`container-type: inline-size` on the card) lay the forms out by the widget's own width, not the viewport's, so a sidebar gets the phone layout. The chart gets a firmer frame in the accent, lighter house lines and the lagna house tinted, all by CSS over the API's classes.

18. **The birth form.** One type-ahead place search (decision 16, unchanged) is the primary field; after a pick the resolved place, its coordinates and its zone (or "worked out from the coordinates") are shown under it, and "Edit coordinates" opens latitude, longitude and an optional IANA zone. No city list: `city="…"` pre-fills the search with a bundled city. Date as day / month / year selects (English months short, so they fit a third of a phone), time as hour / minute / AM-PM, or `time-format="24"` (`data-time-format`, `configure({ timeFormat })`) for 0–23; AM/PM has no default, because a silent AM is a wrong chart. Name and gender are optional; gender is not sent (the API takes none). Validation is per group (date, time, place) with a message under the group in en/hi, `aria-invalid` and `aria-errormessage` on its fields, the first invalid field focused, and each message cleared when its group changes; nothing is sent until all three are right. A real calendar check (31 February is refused) uses UTC arithmetic on the components only. **Remember:** a valid submit stores the entry on the device (`localStorage`, key `kj:birth:v2:<slot>`, strings only, every access in try/catch) and the next visit fills it in with a "Clear" link; the match form stores each side under its own slot. 20. **The loader** (plan §5). `dist/v1.js` is an IIFE of about 1 KB gzipped: a tag → chunk table written in by the build, a scan of the page (`getElementsByTagName` per tag, then a `MutationObserver` until every chunk is asked for), and `import()` of the chunk for each tag found. Chunks are one esbuild ESM build with code splitting (`kj-<element>-<hash>.js`, shared code in `kj-core-<hash>.js`), flat beside the loader, resolved against the loader's own URL (`new URL('.', currentScript.src)`, the query dropped) or `data-chunks` when the tag has it. Each chunk exports its element class and `configure` / `configureFromDataset`; the loader hands the first chunk its tag's `data-*` as they are, so the parsing rules stay in `config.ts`, and replays any later `KJWidgets.configure()`. `KJWidgets.define()` loads everything (0.1.0's meaning); `KJWidgets.load(tag)` loads one, for a tag inside some other shadow root. A chunk that fails to load warns once and is asked again on the next scan. Module scripts are fetched with CORS: the CDN must send `Access-Control-Allow-Origin` (a WordPress plugin is same-origin; `cdn.kaaljyoti.com` sends `Access-Control-Allow-Origin: *`). `dist/index.js` is still one ESM file with every element and `define()`, for bundlers. `dist/cdn-files.json` lists the loader, the pinned copy, the tag table and every chunk; the WordPress build copies from it (and delete the chunks of an older build first). **Budgets** (`scripts/size.mjs`, CI): loader 6 KB, each element chunk 10 KB, each shared chunk 24 KB, and each element's whole page — loader, chunk and every shared chunk it imports — 40 KB gzipped. At the revamp: loader 0.9 KB; a panchang page 25.1 KB, a horoscope page 24.3 KB, a chart page 22.3 KB, the kundli report 38.6 KB (the form, the search, five tabs and the chart). _Stage 2:_ loader 1.2 KB (the table has 22 tags); the new pages and the budgets in decision 24.

Inside the kundli report the state fills only the tab whose request was refused. _Revised 5 October 2026 (credits):_ no plan gates a route any more, so the card a widget meets is the monthly limit (`quota_exceeded`: "Monthly limit reached — This key has used up its credits for the month"); `plan_required` is left for a PDF on the Free plan ("PDFs are available on every paid plan; you are on Free" — `needsPaidPlan()` — drawn as "Available on a paid plan") and for a PDF's own `branding` below Enterprise, the one message that still names a plan (`requiredPlan()` reads it). 23. **The server proxy** (stage 2; revised 2 October 2026). Some routes are closed to publishable keys whatever the plan (`pubAllowed: false` in the gateway): `/v1/transit/scan`, `/v1/match/batch` and the PDFs (decision 27). A widget on one asks the site's own endpoint, which calls the API with the site's secret key. _Revised:_ `/v1/panchang/month` and `/v1/ephemeris/month` were closed too until the owner opened them to publishable keys on 2 October 2026 (still heavy: ten a minute, and 20 credits each); `<kj-panchang-month>` and `<kj-ephemeris>` now call them directly with the publishable key, and through the proxy only when the page has one (`PROXY_PREFERRED` in `core/call.ts`), so the WordPress plugin's transient cache still saves the site's credits. They no longer show the "needs a server proxy" state. **Configuration:** `proxy="…"` on the element, else `data-proxy` on the script, else `configure({ proxyUrl })`; an `https://` URL or a site path (`/wp-json/…`, `/wp-admin/admin-ajax.php?action=…`) — anything else (`javascript:`, `//host`) is no proxy. `data-proxy-all` / `configure({ proxyAll: true })` sends _every_ request through it, for a page with no key. `proxy-docs` / `data-proxy-docs` / `configure({ proxyDocsUrl })` is the owner's link in the no-proxy state (default `https://kaaljyoti.com/api/docs/widgets#proxy`). **Without a proxy** the widget paints a `proxy_required` state ("Needs a server connection — This widget needs the Kaal Jyoti WordPress plugin or a server proxy on this site." and "Site owner: see the setup guide") and sends nothing. **The contract**, for stage 3 (WordPress) and anyone writing their own:

    - **Request.** `POST {proxy}`, `Content-Type: application/json`, `Accept: application/json`, `X-KJ-Client: widgets/<version>`, `credentials: same-origin`, **no key**. Body `{"path": "/panchang/month", "body": { … }}` — `path` is the API route after `/v1`, `body` the JSON body the widget would have sent (`latitude`, `longitude`, `timezone?`, `place?`, `month`, `options: {language: ["en","hi"]}`, and `system` for the ephemeris). A `GET` route (only `/v1/places`, and only with `proxyAll`) arrives as `{"path": "/places", "query": {…}}`.
    - **What the proxy must do.** Allow only the paths it means to serve — the server-only routes, the two months it caches, or with `proxyAll` the widgets' routes; refuse anything else. Refuse a body over 16 KB. Call `POST https://api.kaaljyoti.com/v1{path}` with `Authorization: Bearer kj_live_…` (never the key in the query) and `Content-Type: application/json`, passing `X-KJ-Client` through. Rate-limit per visitor (IP): the heavy routes cost the site's credits (20 each), and the API's heavy bucket is per key, shared by every visitor. May cache an answer by `path` + canonical body (the month routes are deterministic for a place and month; 12 hours is safe).
    - **Response.** Relay the API's status code and JSON body **as they are** (the `{status, data, meta}` / `{status, error}` envelope), with `X-KJ-Plan`, `X-KJ-Request-Id` and `Retry-After` when present. The widget reads it exactly as a direct answer, so a `402 quota_exceeded` for a site out of credits becomes the monthly-limit card and a `429` the one retry. A proxy need not relay `X-KJ-Credits` or `X-KJ-Credits-Remaining`, and must not put the second in a page: it is the account's balance.
    - **The proxy's own refusals** use the same envelope: `{"status":"error","error":{"code":"proxy_path_not_allowed"|"proxy_rate_limited"|"proxy_error","message":"…"}}` with 403, 429 (and `Retry-After`) or 502. They render as the generic error line; a proxy that is misconfigured is the site owner's to see in the network tab, not the reader's.
    - **No nonce is required**: the endpoint is read-only and allowlisted, and a nonce in the URL would break page caching. A plugin that wants one can put it in the URL it writes into `data-proxy`; the widget sends that URL as given.

    No plan refuses a heavy route any more (they have their own ten-a-minute limit and a price of 20 credits), so the refusal a proxied month can meet is `402 quota_exceeded`, the monthly-limit card (decision 22). A publishable key that reached one of these routes anyway gets `plan_required` "publishable keys cannot call this route", which the card words as "cannot be shown in a web widget".

26. **Restyled by the site** (owner requirement, stage 2). Sites put the widgets in their own themes; they must stay presentable. **Own width:** every layout is by container query on the card (`container-type: inline-size`), never the viewport — tested at 280px and 1400px; on a wide block the card stops at `--kj-max-width` (72em) and centres, readings stop at a reading width. **Base size:** `clamp(15px, 1em, 18px)` of the page's size (`--kj-size` fixes it): a 20px page gets 18px widgets, a 13px page 15px. **Partial overrides:** tints and borders already derive from `--kj-accent` and `--kj-text`; text on the accent is now worked out from the accent (`oklch(from var(--kj-accent) …)`, white below lightness 0.68, near-black above), so a page that sets only a pale brand colour keeps readable buttons and tabs; a page's own `--kj-on-accent` still wins. **Fonts:** `font="inherit"` / `data-font` / `configure({ font })` — the element reads the page's stack and uses it for body and headings, with the Devanagari faces behind it for Hindi. **Dark pages under `auto`:** the element reads the text colour it inherits and sets `data-scheme="dark|light"`, which the auto theme's hues follow — a transparent widget on a dark site that never declared `color-scheme` no longer draws maroon on near-black. 27. **PDF downloads through the proxy** (stage 3, 30 September 2026). `POST /v1/pdf/kundli` and `/v1/pdf/match` are on every paid plan (not Free; 1,000 and 500 credits, and one PDF of the month's cap — Starter 50, Growth 200, Scale 500, Enterprise 2,500) and refused to publishable keys, so a PDF is a proxied request like the months (decision 23), with two differences: the answer is the file (`application/pdf`, `Content-Disposition: attachment; filename="…"`), and the proxy must say it relays PDFs. **Offer:** `data-pdf` on the script (`basic`, `professional`, both, or `on` for `basic`) / `configure({ pdf })` names the kundli editions the site offers; with no proxy, or none named, there is no bar. `pdf="off"` on an element hides it there, and a list on the element can narrow the site's editions but never widen them. **The bar** sits under the kundli report's name and under the match score: an edition select when there is a choice (the match PDF has no edition), a language select (English / Hindi, defaulting to the widget's), and a quiet "Download PDF" button that reads "Preparing the PDF…" while it waits. **Request:** `{"path": "/pdf/kundli", "body": {birth, options: {language}, edition, name?, template?, chart_style?}}` — `name` from the form, `template` the element's preset (the four presets are the four PDF templates by name), `chart_style` only `north` or `south`; the match sends `{bride, groom, options, name?, partner_name?, template?}`. No branding, sections or vargas: those are the account's (the dashboard's branding page), not the page's. **Answer:** a PDF is saved through an object URL under the API's filename (only `[\w.-]+\.pdf` is kept, else `kundli.pdf` / `match.pdf`); `403 plan_required` is the plan-required card (decision 22: a site on the Free plan, "Available on a paid plan"), `402 pdf_quota_exceeded` a plain line that the site has made this month's PDFs, a `429` (the API's or the proxy's `proxy_rate_limited`) a line asking to wait a minute, anything else a generic line; each also fires `kj-error`. **Weight:** the bar, its words and its rules are `core/pdf.ts`, loaded with `import()` the first time a form has a bar to draw, and it imports nothing at run time (a module the element chunks share, imported from a new entry too, is split into a chunk of its own and costs every page a file); the rules travel in the bar's own `<style>`. What every page pays is `data-pdf`'s word list in the config; the forms carry `core/pdf-offer.ts` (the offer, and the request's error mapping). The kundli report's page is 39.7 KB of 40 and `<kj-varshphal>`'s 40.0 (39.9 before); no budget was raised.

29. **Zodiac sign icons** (owner request, 5 October 2026; widgets 0.2.0). The Unicode glyphs (`♈︎`…) looked different on every visitor's fonts and were not appealing; every sign is now an icon the widget draws. **Themes** (`sign-icons` on the element or any ancestor, through shadow roots, so a reading inside the kundli report follows the report; else `data-sign-icons` / `configure({ signIcons })`; default `element`): `element` — the sign's symbol on a rounded tile with a soft inner circle, stroked in its element's deep colour (fire Aries, Leo, Sagittarius; earth Taurus, Virgo, Capricorn; air Gemini, Libra, Aquarius; water Cancer, Scorpio, Pisces — the index modulo four); `glyph` — the symbol in a thin ring, one colour (`--kj-sign-glyph`, the accent); `devanagari` — the Hindi name in a double-ring seal (the owner's short spellings: वृष, कुम्भ), and on a Hindi page the picker prints no second name under it (it stays for screen readers); `custom` — the site's own images: a URL template with `{sign}` (`aries` … `pisces`) or a map, or a JSON map in `data-sign-icons` (what the WordPress plugin writes); a map may name the page's default as `theme`, and its images are then used only where an element asks for `custom` (a WordPress block's per-block choice). **Sizes:** `l` in the horoscope's picker (about 46px), `m` beside a value in a tile and in a reading's or horoscope's heading (2em), and the compact inline form in tables (1.3em) — the symbol alone in its element's ink for `element` and `devanagari` (a seal at text size is unreadable), the glyph colour for `glyph`, the image for `custom`. **The symbols** are ours: twelve stroked paths on a 24-unit square (stroke 1.9, round caps and joins; 2.1 inline), one path each, checked crisp at 20, 32 and 48px. From the owner's draft, Virgo's third arch now closes in a loop that crosses its stem and leaves as a short tail (the classical form; the draft's open hook read as a second Scorpio), Scorpio's arches match Virgo's so the pair differ only in the tail, and Capricorn is one stroke — the V, then the stem curling into the fish's loop with its tail out to the lower left — moved 0.6 units right to sit centred. **Custom images** are `<img>` with the sign's name as alt text (Hindi on a Hindi card), built with the DOM and never inlined, so a site's SVG cannot put markup in the widget; only `https:` and same-origin paths are used (`http:`, `data:`, `//host` and any other scheme are refused), a sign the template or map lacks falls back to `element`, and so does an image that fails to load. **Colours** are custom properties on `:host`, so a page beats them: `--kj-sign-<fire|earth|air|water>-<bg|circle|ink>`, `--kj-sign-glyph`, `--kj-sign-ring`. `classic` and `modern` take the owner's palette; `traditional` leans to saffron and gold; `minimal` is one ink (`--kj-text`) with no tint and a hairline ring; dark cards (and `auto` on a dark page) get deep tiles and light strokes. **The chosen sign** in the picker is an accent ring and the name in the accent, no longer an accent fill, so every theme's tile stays legible on it. **Markup and weight:** `signIcon()` in `ui.ts` prints an empty `<span class="kj-zi" data-zi="leo" part="sign-icon">` (`kj-sign` is the chart SVG's class, so not that), and `core/signs.ts` draws into it — a chunk of its own with its own sheet, imported by nothing at run time (decision 27's rule), fetched by the base class the first time a shadow root holds a placeholder and kept drawing through repaints by a `MutationObserver`. The horoscope imports it statically, since its picker is its first paint (its page is 27.8 KB). The placeholder's size is in `base.css`, so nothing moves when the drawing lands. To make room in the shared core (the kundli report's and varshphal's pages were 40.0 and 40.2 KB before this, over the 40 KB budget), eleven unused chrome words were removed, the horoscope's words moved to its own chunk and the daily widgets' words (limbs, windows, sun) to `core/daily-words.ts`, and the report's name line and Vimshottari band rules out of `base.css` into the kundli form's sheet (`report.css`; `dasha.css` keeps its own copy of the band). Pages now: the kundli report 39.5 KB, varshphal 39.4, the heaviest calculators 38.2; the icons' chunk (3.4 KB) is loaded on top of those only once a result with a sign is drawn, as the tables' sheet is. No budget was raised.
